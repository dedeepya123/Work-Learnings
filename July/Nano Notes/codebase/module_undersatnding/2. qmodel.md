## create_qc_model 
- ### create_qc_model() (inside Gemma4Context)

- Uses the **context manager pattern** to perform profiling and temporary model adaptations during model creation.
- Two context managers are used:

#### 1. `event_marker("FP model adaptation & creation")`
- Profiles the execution block.
- Captures metrics such as execution time, memory usage, and other performance information for the model adaptation and creation process.

#### 2. `_patched_gemma4_classes(self.adaptations)`
- Temporarily monkey-patches Gemma4 classes/functions with Qualcomm-specific implementations.
- Applies the patches before the model is instantiated.
- Uses `yield` to transfer control to the code inside the `with` block.
- Once the `with` block completes, execution resumes after `yield` and the original Gemma4 classes/functions are restored in the `finally` block.
- Restoration happens even if an exception occurs during model creation.

#### Execution Flow

1. Start profiling (`event_marker`).
2. Apply Gemma4 → Qualcomm-specific patches.
3. `yield` transfers execution to the `with` block.
4. Load Gemma4 model using the patched implementations.
5. Perform additional model adaptations (e.g., `_vision_mha_to_sha()`).
6. Exit the `with` block.
7. Restore original Gemma4 classes/functions.
8. Stop profiling and record metrics.

#### Key Learning

`yield` inside a context manager acts as a pause point:
- Code before `yield` = setup phase.
- Code inside the `with` block executes while the context is active.
- Code after `yield` (typically in `finally`) = cleanup phase.

#### Mental model:

Setup → yield → Execute with-block → Resume → Cleanup
